## Correctness

As analyzed in both `training.md` and `evaluation.md`, most of the core functionality correctly implements ngram training and preplexity calculations according to our textbook. The LLM's model performed slightly better than my model, with perplexity scores around 1-2 units lower than all my results.

However, there are deviations, such as using log perplexity not mentioned in the textbook, and mistakes, such as inserting the incorrect number of start/end tokens, that results in an imperfect solution by the LLM. It still makes mistakes, which for this assignment is slightly fewer than me. So while the result could be considered "more correct" in terms of better perplexity performance, it also made a really simple mistake for a pretty straightforward assignment.

LLMs cannot "think", they don't having rationals or the ability to reason about topics. As covered in the LLM lecture & slides, all it does is take a prewritten prompt and predict the next likely word/token in the sequence over and over. The more examples of a question appears in the training data, the more likely the LLM will generate a correct output. This means that "easy" questions, common examples (e.g. fibonacci number) with tons of implementations, is easy to copy from and generate. This also means that "hard" questions, long and/or complex challanges with many moving parts and considerations, fails more dramatically in proportion to how many examples actually exist and contained in the training data. Hence, for a relatively simple program to train and evaluate ngrams, the LLM can produce a (mostly) correct output thanks to tons of examples online that it learned from.

Going back to correctness and how LLM's don't "think", it also doesn't consider future functionality outside it givens prompt. As noted in `architecture.md`, having functions specifially for uni/bi/trigram training and evaluating means the code can't generalize to higher degree ngrams. Context is stored separately for bigram and trigrams, making the model file rigid and harder to modify. A more correct solution would consider these possibilities when beneficial, like my `find_ngram()` function that works on any arbitary n degree and so can be reused for uni/bi/trigrams. Good programmers consider these optimizations when designing their programs, which LLM's can't ever know unless said solution is in their training data.

## Style

Despite any bias from comparing the style between my work and the LLM's, I say my style is still better overall. Looking at my analysis from architecture.md and style.md, my code is more concise, readable, and reusuable to other humans.

Both of the LLMs files are twice as long as mine (with an extra utils.py for more logging), despite achieving the same functionality. This is due to all the extra functions, docstrings, comments, and debug print statements added throughout. Consider evaulation, where I contained all my logic inside main(), using conditional checks to manage different model and types. In contrast, the LLM breaks each branch into well documented functions like `compute_[unigram|bigram|trigram]_perplexity()`, with additional helper functions like `read_data()` and `add_boundary_marker()`. For what should be a linear and simple process of:

read dev file -> load model -> perplexity for each line in file -> print result

the LLM's code is excessively overcomplicated and harder to read. Having to jump between lines to read and debug functions is a bigger hassle, especially as they get nested within other functions, than laying it out flat in main(). Like reading files and adding boundary markers takes less than 10 lines of python code, and should be really obvious to any programmer just looking at it. 

The LLM also doesn't reuse its functions more than once, where as all my functions were designed to be reused for different degree ngrams. For training I reused find_ngram() and counter_to_normalized_json() 5 times for each model and laplace smoothing. Counter to json also takes in 5 parameters so it can generalize to works with multiple degrees of n. Contrast this to the LLMs many functions which only takes in one parameter and nothing else (e.g. the utterance array), and this only adds onto the excess fluff problem that LLM programs already have.
